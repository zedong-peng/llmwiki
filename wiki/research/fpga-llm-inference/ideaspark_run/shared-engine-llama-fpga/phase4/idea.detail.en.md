# Visibility-Sensitive Command Streaming for Native GGML FPGA Inference

**Method.** Visibility-Sensitive Trace Compression (VSTC)

## Motivation
**Problem framing.** The central bottleneck is a control-plane mismatch in native, low-batch FPGA inference: a GGML trace contains calls whose results must remain observable to the host or participate in mutable state, alongside a larger data-plane bulk whose intermediate completions are not semantically required. Treating both groups as equally observable turns a semantic precaution into repeated XRT launch traffic. The primary instance is llama.cpp running Gemma 3 1B F16 on a U280, but the issue is structural for native tensor runtimes whose call graph and buffer identities are only known at execution time.

Prior FPGA LLM work improves the data plane rather than representing this runtime distinction. LlamaF [openalex:W4405909140] uses model-specific matrix concatenations and W8A8 kernels while keeping attention control and KV-cache work on the processing system; Big PE [openalex:W4416342314] increases systolic-array density for prompt processing; and XtraMAC [arxiv:2605.06052v1] improves mixed-precision MAC utilization. These approaches can reduce computation cost, but none supplies a per-original-call decision record that establishes when native completion, allocation identity, alias behavior, state, and explicit errors may be preserved while launch submission is compressed.

**Why now.** Recent FPGA LLM work makes the remaining control-plane gap more visible: Big PE [openalex:W4416342314] and XtraMAC [arxiv:2605.06052v1] each push the compute datapath toward higher density or better datatype utilization, so host dispatch becomes a more consequential fraction of low-batch latency rather than an incidental overhead. At the same time, llama.cpp exposes a stable native GGML call stream and XRT provides the command and completion interfaces needed to capture it, while U280-class boards can host a small resident interpreter without replacing the installed F16 kernels. These conditions make it practical to test a runtime representation change directly instead of inferring its benefit from a model-specific accelerator redesign.

**Why prior work stopped.**
- `openalex:W4416342314` (arXiv 2025-09): Big PE [openalex:W4416342314] co-designs a denser 4x4 8-bit coarse-grained systolic cell for TinyStories prompt processing on PCIe-based FPGAs.
  - _Did not do_: It does not preserve a native F16 GGML call stream through a per-call visibility partition or reduce launch submissions while retaining each original call's completion and error semantics.
  - _Structural reason_: Its optimization unit is a compute-array mapping, which has no runtime representation of host reads, aliases, state, or consumer visibility from which safe command admission can be decided.
- `openalex:W4405909140` (arXiv 2024-11): LlamaF [openalex:W4405909140] accelerates Llama2 with model-specific Wq/Wk/Wv and W1/W3 concatenations plus two W8A8 GQMV kernels, while retaining attention control and KV-cache handling on the processing system.
  - _Did not do_: It does not construct patchable exact templates from the live GGML trace or give every original call an individually surfaced completion after eligibility is established.
  - _Structural reason_: Static matrix grouping is defined before execution and therefore cannot encode the dynamic host-observation, alias, state, scratch, allocation, and explicit-error facts required for native-runtime command compression.
- `arxiv:2605.06052v1` (arXiv 2026-05): XtraMAC [arxiv:2605.06052v1] builds a datatype-adaptive mixed-precision MAC that shares mantissa products to improve FPGA DSP utilization.
  - _Did not do_: It does not alter the host command representation or suppress repeated XRT submissions when the same F16 data-plane kernels are retained.
  - _Structural reason_: A MAC microarchitecture has no control-plane mechanism for deciding whether a runtime call may defer host-visible materialization without changing native behavior.

**What changes when the gap closes.** Closing this gap would let a native llama.cpp backend retain its original tensor allocation and explicit-error contract while avoiding per-call host launches for device-only portions of prefill and decode. That creates a reusable runtime path across model traces instead of requiring each new model to be recast into a bespoke matrix schedule, complementing the data-plane advances in LlamaF [openalex:W4405909140] and XtraMAC [arxiv:2605.06052v1]. It also makes a concrete systems claim available: latency improvements can be attributed to a measured reduction in semantically unnecessary submissions, rather than to an inseparable accelerator redesign.

## Method
**Pipeline.** VSTC first observes the native GGML/XRT execution stream and records a ticket for each original call rather than assuming that calls of the same operator type have the same safety conditions. It evaluates those tickets to retain host-visible or stateful calls as H boundaries and to admit only device-only calls as B entries. Consecutive B entries are encoded as exact, patchable device bytecode and interpreted by a resident engine, while H calls keep individually surfaced completion and explicit-error behavior. The backend then audits the resulting execution against the native trace and relates latency changes to rho, the fraction of baseline submissions represented by admitted B entries.

### ticketing_and_partition
*Record what each native call exposes, then split the trace into host-visible boundaries and safe device-only bulk.*

1. **Capture native call tickets** (`S1`)
   - Insert a tracing shim at the GGML backend-call layer and the Xilinx Runtime event layer so every original call receives a stable $call_{id},$ operator name, tensor handle list, buffer-object id, byte offset, byte extent, queue id, dependency-event ids, completion-event id, return code, and explicit error payload. For each call, construct the visibility-sensitivity ticket from concrete runtime facts: mark host-read when any mapped CPU read, synchronization-for-read, or logits/materialization read can observe the call's output before the next admitted-only consumer; mark alias when two live tensor views or XRT buffer-object regions overlap in bytes; mark state when the call mutates backend-global state, allocator state, command-queue ordering state, kernel configuration state, or persistent scratch ownership; mark unique-consumer only when the dynamic use graph has exactly one downstream device consumer before any host-visible boundary; mark original-allocation when the output stays in the caller-provided tensor allocation and buffer-object region; mark scratch when the call needs temporary storage whose lifetime or address is externally shared across calls; mark explicit-error when the native call can synchronously return, raise, or record an error that the host can observe at that call boundary. Emit the ordered ticket trace as append-only JSONL keyed by $call_{id},$ preserving the native execution order and linking each ticket to the original XRT submission and completion events.

*Visibility-sensitivity ticket for original GGML call i: host-read, alias, state, unique-consumer, original-allocation, scratch, and explicit-error facts.*
$$ \tau_i = (r_i,a_i,s_i,u_i,o_i,q_i,e_i) \tag{1} $$

   - _Why:_ The heterogeneous-decomposition decision must be made from runtime semantics rather than from a static operator name or model-specific matrix group.
2. **Partition observable boundaries** (`S2`)
   - Evaluate the admission predicate as a pure pass over the ordered ticket trace, producing one decision record per $call_{id}$ with fields $\{call_{id},$ class, $denied_{reasons}, predecessor_{ids}, successor_{ids}\}.$ Classify a call as a host-visible boundary H when any ticket hazard is present: host-read, alias, state mutation, non-unique consumer, non-original allocation, scratch hazard, or explicit-error exposure. Classify it as a bulk device-only entry B only when the ticket satisfies all required safety facts; never infer safety from the operator type alone. Build $predecessor_{ids}$ and $successor_{ids}$ from the dynamic tensor-use graph and XRT event dependencies, then split the trace into maximal contiguous runs of B entries separated by H boundaries. For every denied B admission, store the exact failed ticket fields rather than a prose explanation so later auditing can replay the decision mechanically.

*Admission predicate: only a call with no host-read, alias, state, scratch, or explicit-error hazard and with a unique consumer and original allocation can enter a B template.*
$$ b_i = \mathbb{1}[\neg r_i \land \neg a_i \land \neg s_i \land u_i \land o_i \land \neg q_i \land \neg e_i] \tag{2} $$

   - _Why:_ The partition prevents command compression from crossing the visibility, alias, state, allocation, scratch, or error conditions that define the native contract.

### template_streaming
*Turn eligible bulk into exact streamed templates and run them while keeping boundary behavior visible.*

3. **Build exact B templates** (`S3`)
   - For each maximal B run, serialize an exact B-template record whose header stores $template_{id},$ ordered $call_{ids},$ required kernel identifiers, argument-slot table, buffer-object bindings, byte offsets, tensor shapes, strides, element types, dependency-event slots, completion slots, and patch locations for runtime values that change between invocations. The bytecode body is not a fused mathematical operator; it is an ordered sequence of existing F16 kernel invocations and XRT command descriptors with symbolic slots that are patched from the current GGML tensor bindings immediately before dispatch. Preserve one completion slot per original $call_{id}$ so the resident interpreter can mark call-level completion in native order even though the host submits the whole B run as one streamed template. Reject template construction if any required binding cannot be represented as a stable buffer-object id plus offset/extent pair, and send that call back to H by recording $a \mathit{template\_build\_denial}$ reason.
   - _Why:_ Exact templates retain the installed F16 kernels and caller allocation semantics while eliminating repeated host-side reconstruction of device-only submissions.
4. **Stream bulk and surface boundaries** (`S4`)
   - Execute the final H/B stream with a resident interpreter that owns a template cache and an in-order completion ledger keyed by original $call_{id}.$ When the next item is H, submit the original native GGML/XRT call unchanged, wait or surface completion exactly as the native backend would, copy through its return code and explicit error payload, and flush any prior B completion slots that must become visible before that boundary. When the next item is a B-template record, patch its symbolic argument slots from the current tensor bindings, enqueue the encoded command sequence to the resident interpreter, execute the existing kernels in the recorded order, and update the per-call completion ledger without exposing intermediate host completions unless a later H boundary requires them. Produce logits, tensor side effects, completion states, and explicit-error traces in the same $call_{id}$ order as the native trace, with any interpreter-side internal failure mapped back to the earliest affected original $call_{id}.$
   - _Why:_ This realizes the claimed launch reduction without turning the resident engine into a generic asynchronous scheduler that hides native runtime observability.

### equivalence_and_measurement
*Check that the streamed path still matches native outputs and measure whether admission actually helps.*

5. **Audit equivalence and admission** (`S5`)
   - Run three matched executions for the same prompts, model weights, tensor allocations, and XRT configuration: the native backend, VSTC with the admitted H/B stream, and VSTC with every candidate B admission forced back to individual completion while keeping the resident interpreter path otherwise identical. Compare logits byte-for-byte at the final output tensor and compare explicit-error traces as ordered tuples of ${call_{id}, return_{code}, error_{payload}}$; any mismatch fails equivalence and is reported with the first divergent $call_{id}.$ Compute $\rho $ from the stored decision records as the fraction of baseline XRT submissions represented by admitted B-template entries, count actual XRT submissions in each execution, and report p50 and p95 latency for prefill and decode from timestamped run records with warmup runs excluded by a fixed preregistered rule. The full-observation oracle is implemented by re-running with all ticket host-read facts forced true, which should collapse B admission and reproduce the native completion/error trace; the forced-denial control isolates whether latency changes track the admitted fraction rather than the interpreter path alone.

*Admission fraction rho, the share of baseline XRT submissions represented by admitted B-template entries.*
$$ \rho = \frac{\sum_{i=1}^{N_{\mathrm{XRT}}} b_i}{N_{\mathrm{XRT}}} \tag{3} $$

   - _Why:_ The full-observation oracle and forced B-denial control test whether any speedup comes from visibility-sensitive admission rather than from an unmeasured interpreter or changed kernel path.
